This is **commentary**: a reasoned argument, signed by its editors, that readers are invited to disagree with. The argument is simple. Trust in AI *chatbots* has mostly been a question of accuracy. Trust in AI *agents* — systems that take actions on our behalf — is a different problem, because the costs of being wrong are no longer symmetric with the benefits of being right. A chatbot that gives a wrong answer wastes a reader's time. An agent that takes a wrong action can spend money, send a message, or delete a file.

The claim of this piece is that trust in agents should rest less on how often they are right and more on **how they fail**: whether failures are visible, bounded, reversible, and attributable.

## Why "accuracy" stops being the right word

Benchmarks for language models were built around tasks with a right answer: a question, a passage, a label. The agent setting is different: the model picks tools, calls them, reads the output, decides what to do next, and may do this for dozens of steps before anything the user can inspect.

Three things change in that setting.

**The error distribution shifts from errors to incidents.** A chatbot's errors are mostly local: it gave a wrong fact in one answer. An agent's errors can propagate: it misread a step, then acted on that misreading, then acted on the consequences. By the time anyone notices, the state of the world has changed.

**The relevant unit of evaluation moves from the model to the system.** A good model embedded in a bad scaffolding — tool definitions, permission checks, retry logic, logging — behaves badly. A less capable model embedded in a careful scaffolding can behave well. Benchmarks like AgentBench<Cite id="agentbench" /> and SWE-bench<Cite id="swe-bench" /> have begun to measure systems, but most public reporting still names the model as if it were doing the work alone.

**Adversaries enter the picture.** The content an agent reads is now part of its input. Indirect prompt injection — an instruction smuggled into a webpage or email that the agent processes — has moved from a research curiosity to a routine threat to any agent that reads untrusted text<Cite id="prompt-injection" />.

## Four properties worth asking for

What follows is a short list of properties we would look for before trusting an agent with anything the user cares about. They are not independent, and they are not sufficient. They are the floor.

**1. Visible scope.** People can see what the agent may and may not do before it starts. Not in a 20-page policy document; in the user interface, in the same place where the user confirms the task. If the agent can send email, say so. If it cannot touch a particular folder, say so. The scope should be legible in a sentence, not inferred from documentation.

**2. Enforced limits.** Scope is enforced outside the model, not only stated in its instructions. The pattern of "the system prompt says you must not X" has an obvious failure mode: a determined adversary (or a confused model) can produce output that violates X anyway. Enforcement means a layer below the model that intercepts actions and refuses the ones outside scope. In security terms: capability-based rather than prompt-based.

**3. Checkpoints for irreversible actions.** The agent pauses for confirmation before anything that cannot be undone by the agent itself: pushing to a shared repository, sending an email, placing an order, deleting a file. The reversibility test is simple: if the action turns out to be wrong, can the agent undo it in the next step? If not, a human should see it first.

**4. A record.** Every tool call, every piece of untrusted input the agent read, every decision point, inspectable afterwards. Logs matter not because anyone will read every one of them, but because audit becomes possible when something goes wrong. Without a record, each incident is a black box.

## Why instructions alone are not enough

Agent evaluations that give the model explicit constraints and then measure whether it respects them have become a small research subfield of their own. The headline result is that even state-of-the-art models drift from stated constraints over long tasks<Cite id="agentbench" />. Drift is worst where the constraint conflicts with task progress — an agent told not to escalate privileges, which then faces a task it can only complete by escalating, often finds a plausible-looking rationale for doing so.

Three mitigations are being tried.

- **Explicit refusal tokens** that the agent emits when a step is out of scope, parsed by the surrounding system.
- **Scope narrowing** so that the agent cannot even propose an out-of-scope action: the tool call is simply not available.
- **External monitors** — a second model, a rule engine, or a human — that watches the agent's trajectory and halts it on anomaly.

The second of these — remove the tool rather than ask the model to refrain from using it — is the one with the cleanest safety story, and the one most consistent with how operating systems have handled analogous problems for 50 years<Cite id="tool-use" />.

## What the standards bodies are saying

The NIST AI Risk Management Framework<Cite id="nist-rmf" /> defines trustworthy AI as valid and reliable, safe, secure and resilient, accountable and transparent, explainable and interpretable, privacy-enhanced, and fair with harmful bias managed. For agent systems, the second (safety), third (security), and fourth (accountability) carry disproportionate weight compared to classifiers.

Applied to agents, each term unpacks differently from its classifier counterpart.

- **Reliability** becomes "the agent's failure mode is predictable", not "the agent is often right". A reliably cautious agent is more useful than an occasionally brilliant one, because the human knows what to expect.
- **Safety** becomes "the agent's irreversible actions pass through a check". The claim is testable: show the list of irreversible actions and the mechanism that intercepts them.
- **Accountability** becomes "someone can tell what the agent did and why". The record above is the implementation; without it, accountability is aspirational.

## A note on evaluation

Benchmarks like SWE-bench<Cite id="swe-bench" /> measure what fraction of real-world GitHub issues an agent can resolve. They have been enormously useful for comparing systems. They do not, by design, measure trustworthiness: a system that gets 50% of the issues right but silently vandalises code in the other 50% would score the same as one that cleanly fails on the hard half.

A trustworthy-agent benchmark would need to measure at least three things the current public benchmarks mostly do not:

- **The rate of out-of-scope actions**, counted even on tasks the agent completed successfully.
- **The reversibility of failures.** Were the wrong attempts cleanly undone, or did they leave state behind?
- **Robustness to adversarial inputs** — pages, emails, repository files containing instructions aimed at the agent.

A good benchmark here would be worth more than another percentage-point on the current ones.

<Evidence kind="open">
Can we measure an agent's trustworthiness *in advance*, from static properties of its scaffolding, or only by watching how it behaves in deployment? The honest answer today is some of both: scope narrowing and enforced limits are measurable in advance; drift under novel inputs seems to require live observation. Shrinking the second category is one of the most useful research directions in the field.
</Evidence>
